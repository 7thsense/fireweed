# Fireweed Queue v0.22.0 public preview

v0.22.0 surfaces per-request replay-vs-fresh disposition on the API-001
request-id push path so downstream embedders (Snorri create/enqueue counters)
can distinguish a first delivery from an idempotent replay without changing
conflict semantics.

## Request-id push disposition

- `push_batch_with_request_id` now returns `PushBatchOutcome` with
  `disposition: PushDisposition::{Fresh, Replayed}` and the original item ids.
  The disposition is per **request** (one request id covers the whole batch).
- `push_with_request_id` returns `(ItemId, PushDisposition)`.
- Same body + same request id still replays the retained ids (`Replayed`); a
  different body still returns `RequestIdConflict`. No second append on replay.
- `PushBatchOutcome` implements `Deref`/`AsRef`/`From` for the item-id vector so
  callers that only need ids can call `.into_item_ids()` or dereference.

## Breaking change

Call sites that treated `push_with_request_id` / `push_batch_with_request_id`
results as bare `ItemId` / `Vec<ItemId>` must update. Snorri should repin to
`v0.22.0` and use the disposition when closing snorri-4373fbc0 (duplicate
create/enqueue must report `duplicate:1`, not `succeeded:1`).

## Unchanged

- Storage composition, facade erasure, and the rest of the public operation
  surface remain as in v0.21.0.
- Upsert / `UpsertOutcome` remains a separate `client_item_key` mechanism.
- crates.io and GHCR publication remain deferred. This is a GitHub source
  release under `MIT OR Apache-2.0`.

## Headline

`AsyncProjection` BatchUpdate no longer waits for apply to plan. A missing
`ClientItemKey` is logged and resolved at apply (`item_id = 0`). Finalize
validate uses the reader. Apply-start delay stays 300 ms (dropping it
starves ingest).

## Cut contents

- One reader peek for BatchUpdate. No `wait_for_progress` loop.
- `UpdateFieldsCommand` carries optional `client_item_key` / `expected_item_version`.
  Unresolved rows use `item_id = 0`; apply looks up the live key.
- Keep-payload batches do not SELECT or write the blob.
- Class S RelTx runs on `run_reltx_blocking`. `catch_up_produce` remembers
  the produce position it already drained.
- `finalize_validate` is a reader SELECT. No `IMMEDIATE` + rollback.
- SS deliver is sequential claim then complete. Overlapping complete with
  the next claim packed two appends and poisoned apply (`300 → 302`).
  Ordered enqueue is a follow-up.
- `apply_start_delay_ms.max(300)` stays. Without it ingest is ~300/s.

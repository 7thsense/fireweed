## Headline

SQLite and Turso apply a packed log hop through one shared RelTx contract:
one write transaction, coalesced Push, fused claim+complete, and set-based
BatchUpdate (including gates). The SQL projection remains the item store.

## Cut contents

- `fireweed_relational::apply_committed_batch_sql` is the hop apply for
  SQLite-family projections.
- Turso `apply_owned` calls that hop after epoch fence; it no longer has a
  native per-command apply match.
- Set-based `UpdateFields` in one hop become `UPDATE FROM VALUES` plus chunked
  gate delete/insert.
- Request-id outcomes persist in the same apply transaction.
- Reassign writes `fireweed_lease_bearers`; expire deletes them.
- LeaseExpired only unleases rows whose durable expiry is before the command
  timestamp.
- Turso RelTx runs a multi-thread apply hop in one `block_in_place`.
- Postgres apply stays dialect-forked (`$n`, `UNNEST`). Folding it onto RelTx
  needs a SQL dialect layer, not a call to SQLite text.

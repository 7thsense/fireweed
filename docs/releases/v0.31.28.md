# Fireweed v0.31.28 — storage cleanup and correctness

This source-preview prerelease contains storage cleanup and correctness fixes.
**Sustained workflow qualification failed:** both repeated full campaigns timed
out during their seventh cycle. This release does not establish capacity
readiness for a Snorri production migration or product-ready P20pr deployment
qualification. The performance investigation remains open.

The supported storage matrix is four logs (memory, PostgreSQL, filesystem, S3)
by three projections (memory, Turso, PostgreSQL). Retired SQLite implementations,
disabled test paths, duplicated migration tests and unused dependencies are
removed. Useful behavioral tests use the current native Turso implementation.
Compatible dependencies and the site browser-test dependency are refreshed.

Correctness fixes cover sparse log-tail recovery, PostgreSQL claim persistence,
compact-entity mutation planning, retained-row forwarding, Turso row versions
and serialized ID/key batch updates, and lease renewal after asynchronous
claims. The log remains the sole durability authority. Projections remain
reconstructible; workflow enrichment stays on each original row.

Whole-cohort claims now persist their bearer tokens atomically with the lease.
If an older Turso projection already has an active cohort lease with a missing
bearer, rebuild that disposable projection from its authoritative durable log
before resuming workers. Ordinary catch-up skips already-applied commands and
does not repair this prior state. Preserve the log and its request history.

Native Turso now implements discovery, exact and typed index queries, range and
aggregate queries, query claims, gates, scalar rescheduling, selector mutations,
and full logged transitions across the supported log compositions. Query claims
retain receipts through reopen; complete mutations validate before append. The
ordinary unindexed enrichment path retains its bounded generation implementation.
The optional projection-maintenance handle and universally deferred
`side_record_query` capability remain outside this parity surface.

## Current workflow capacity

The representative workflow ingests original rows, enriches metadata and top
times, delivers in bounded chunks with retries, reports progress and final
dispositions, then purges by retention. Enrichment remains on the original rows.

| Serial measurement | Result |
| --- | --- |
| First full campaign, C1 | Failed after 782.963 seconds with an authoritative-log post-position produce timeout; six cycles complete. |
| First primitive suite, P1 | Passed all five operation floors. |
| Repeated full campaign, C2 | Failed after 852.724 seconds with the same timeout category; six cycles complete. |
| Repeated primitive suite, P2 | Passed all five operation floors. |

Neither campaign has a complete eight-million-recipient result, so no full-run
throughput is claimed. Primitive throughput does not substitute for workflow
capacity. Historical passing results from source `49f1b6b` retain that identity
and are not measurements of this release.

A separate four-cycle traced run completed and independently verified/purged
four million lifecycles at **8,638.52 recipients/sec**. It retained 133 failed
qualification checks, including rate misses and checks requiring a sustained
checkpoint regime. Checkpoint attempts reached 10.010 seconds; successful log
produce operations reached 26.021 seconds. These concurrent durations cannot be
added into lost wall time, and successful-only traces do not identify the
operation that timed out in either full campaign.

The completed two-cycle disk/RAM/disk comparison measured **12,383.20 /
15,693.88 / 11,729.11 recipients/sec**, with authoritative logs on disk in every
arm. RAM projection throughput exceeded the mean disk controls by 30.17%, while
sampled host writes fell 53.69%. Each arm passed its diagnostic correctness and
progress checks, but every main database remained 4 KiB: this comparison did not
reach the materialized-main checkpoint regime. Both disk controls missed the
12,500/sec overall floor. Background zram activity and earlier aborted attempts
remain disclosed; no placement arm qualifies the sustained workload.

Fresh 8-GiB disk calibration measured **75.84 MiB/s direct** and **50.55 MiB/s
buffered**. These observations do not establish an indefinite SSD ceiling or
explain the entire application cost. The 10,000 complete-recipient/sec target
and 12,500/sec stretch target remain unmet for this candidate.

See [maintenance verification and performance](https://github.com/7thsense/fireweed/blob/v0.31.28/docs/perf/maintenance-release-baseline.md)
for the hardware arithmetic, measurement limits and remaining investigation.
The [final evidence manifest](https://github.com/7thsense/fireweed/blob/v0.31.28/docs/perf/evidence/maintenance-verification-final-v0.31.28/manifest.json)
preserves successful, failed and interrupted attempts with their original

## Identity policy

The pre-S reserved identity is `v0.31.28`; synchronized workspace packages use
`0.31.28`. Helm source defaults, the independent benchmark tool and gate-set
versions retain their independent coordinates. The live `.ddx` tracker is not
product authority. Before tagging:

```sh
bash scripts/release/list-public-version-sources.sh v0.31.28
bash scripts/release/verify-release-identity.sh --version 0.31.28
```

An explicit source-preview manifest selects the prerelease packaging route.
Releases without that manifest retain the governed deployment gates. This is
not a signed supply-chain or remote-log throughput claim.

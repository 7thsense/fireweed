# pqueue v0.19.4

v0.19.4 is a correctness and under-load scalability release. Publication is
pending the verification checklist below; these notes do not claim that the
governed density or E3 release proofs have passed.

## Correctness and query paths

- Filtered claims now traverse authoritative object-log projections, including
  embedded SQLite after the derived projection is deleted and rebuilt from
  object-log history. Capability reporting matches the implemented SQLite and
  PostgreSQL projection surfaces, and caller-supplied eligibility and lease
  times remain authoritative.
- SQLite hot-query paths use indexed, set-based candidate selection rather than
  repeated per-item scans. Covering bucket indexes, bounded candidate work, and
  chunked typed-index rekeys keep claim, grouped-summary, and update costs
  bounded without weakening query correctness.
- Full-async Turso projection behavior matches the SQLite command, read,
  cancellation, reopen, and local-file-loss contracts. Its server profile and
  focused CI lane remain feature-gated.
- Segmented object-log head publication performs constant metadata work per
  seal. Immutable successor CAS continues to fence stale owners without
  rescanning the complete historical head set.

## Async and relational load paths

- Blocking durable-storage work is isolated from async runtime workers and
  partitioned by queue. Queue-local storage tasks have explicit shutdown and
  failure handling, preventing one slow queue from serializing unrelated queue
  work.
- PostgreSQL compositions share a fixed connection pool instead of allocating
  a pool per active queue. Queue count therefore does not multiply established
  database connections.
- PostgreSQL due summaries, candidate selection, group ranking, ownership
  renewal, and queue migration use bounded vectorized SQL operations. Migration
  and projection writes are chunked, retry-safe, and idempotent; the load path
  no longer performs one database round trip per item or group.

## Portable release evidence

- Scale qualification runs under ordinary concurrent load. Exact outcomes,
  monotonic logical progress, configured `progress_bound_ms`, bounded shared
  resources, same-run controls, and exact recovery are release-significant.
  Absolute throughput, latency, and recovery time are topology-specific
  capacity observations, not host-speed pass bars; no quiet-host deferral is
  permitted.
- The tag gate requires fresh smoke E2/E3 rows and a separately governed
  exact-revision E0-E3 composite. Named density, failover/routing, and E3
  authorities fail closed on omissions, duplicate rows or keys, revision
  mismatches, unlisted substitutes, false bars, or malformed evidence.
- The governed archive is deterministic and SHA-256 verified. Its attestation
  binds the resolved tag, checked-out commit, evidence, producer inputs, and
  review timestamps before packaging begins.
- `objectlog/hybrid-strict` remains experimental through environment or direct
  configuration only. The Helm schema and negative gate continue to exclude it
  from public deployment support.

## Verification required before publication

The release manager must record successful results for all of the following
before creating or updating the GitHub release:

- workspace formatting, tests, warning-denied Clippy, and configured coverage
  gates;
- HELIX graph audit, validation, and staleness checks;
- exact PostgreSQL transaction evidence for the `postgres/sqlite` and
  `postgres/postgres` storage pairs;
- fresh smoke evidence plus the governed exact-revision TP-002 composite and
  exact-tag attestation;
- exact live 1,001-queue object-log/direct-SQLite density evidence under load;
- governed E3 four-bound/two-profile cost, exact 10-million-item recovery,
  fencing, and TP-003 contract evidence;
- Helm, deployment, live-`kind`, release-artifact, checksum, and container-image
  digest gates.

Until those results are supplied, v0.19.4 is a release candidate and no density,
E3 cost, or 10-million-item recovery result from this revision is asserted here.

## Release assets and publication checklist

On the release workflow's Linux x86_64 runner, `target/release-dist/` must
contain this required release set. Any additional regular files are also
checksummed and uploaded:

- `pqueue-0.19.4-x86_64-linux.tar.gz`
- `pqueue-0.19.4.tgz`
- `pqueue-helm-chart.txt`
- `pqueue-service-image.txt`
- `deployment-proof.json`
- `deployment-proof.md`
- `SHA256SUMS`

The governed `<release-commit>.tar.gz` and matching `.sha256` sidecar are tag
gate inputs fetched into `target/`; they are not GitHub release assets.

After every required proof is green, the workflow-equivalent packaging and
local asset verification commands are:

```bash
version=0.19.4
tag=v0.19.4
commit=$(git rev-parse HEAD)
owner=telepathdata
image="ghcr.io/${owner}/pqueue-service"
: "${PQUEUE_IMAGE_DIGEST:?set PQUEUE_IMAGE_DIGEST to the pushed sha256 digest}"

bash scripts/release/package-binaries.sh "$version"
bash scripts/release/package-helm-chart.sh \
  --version "$version" --tag "$tag" --destination target/release-dist

# After the two GHCR tags have been pushed and their sha256 digest is known:
bash scripts/release/write-container-image-evidence.sh \
  --image "$image" \
  --version "$version" \
  --version-tag "${image}:${version}" \
  --sha-tag "${image}:sha-${commit}" \
  --digest "$PQUEUE_IMAGE_DIGEST" \
  --commit "$commit" \
  --dockerfile Dockerfile.prebuilt \
  --output target/release-dist/pqueue-service-image.txt

PQUEUE_RELEASE_VERSION="$version" \
PQUEUE_RELEASE_DIST=target/release-dist \
PQUEUE_IMAGE_EVIDENCE_FILE=target/release-dist/pqueue-service-image.txt \
  bash scripts/ci/deployment-release-gate.sh --finalize-proof
install -m 0644 target/deployment-release-gate/deployment-proof.json \
  target/release-dist/deployment-proof.json
install -m 0644 target/deployment-release-gate/deployment-proof.md \
  target/release-dist/deployment-proof.md
bash scripts/release/write-checksums.sh target/release-dist
bash scripts/release/verify-release-artifacts.sh \
  --version "$version" --commit "$commit" --dist target/release-dist
```

Publication uses the release note itself and every verified file in the
distribution directory:

```bash
gh release create v0.19.4 target/release-dist/* \
  --repo telepathdata/7thsense-pqueue \
  --title v0.19.4 \
  --notes-file docs/releases/v0.19.4.md
```

If the release already exists, update it without silently retaining stale
assets:

```bash
gh release edit v0.19.4 \
  --repo telepathdata/7thsense-pqueue \
  --title v0.19.4 \
  --notes-file docs/releases/v0.19.4.md
gh release upload v0.19.4 target/release-dist/* \
  --repo telepathdata/7thsense-pqueue \
  --clobber
```

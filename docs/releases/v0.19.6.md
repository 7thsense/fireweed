# pqueue v0.19.6

v0.19.6 strengthens pqueue's behavior under sustained load and the governed
evidence used to qualify that behavior. The release removes scalar work from
production batch paths and makes scale and recovery qualification depend on
semantic correctness and bounded resources rather than host speed.

## Changed

- RESP pipelined pushes retain their batch shape through ownership admission
  and downstream storage dispatch while preserving request order and scalar
  command semantics.
- Queue-density operation reuses bounded control-plane work, accounts for live
  tasks and connections, and defers maintenance at the declared task cap.
- The E2 cross-owner authority now requires all three canonical 2/4/8-owner
  sweeps; missing, duplicate, extra, or mixed-configuration sweeps fail closed.
- E3 object-log qualification binds measured request and byte counters, cost
  inputs, fencing, and transaction evidence to the same source revision.
- E3 recovery uses a deterministic size-driven segment shape and validates
  exact state, bounded replay work, and segment-density provenance. Wall-clock
  observations remain capacity data rather than release thresholds.
- PostgreSQL-native command history and projection changes now share one
  transaction, with bounded command reads, resumable snapshot migration, and
  fail-closed recovery checks.
- The production PostgreSQL selector uses a fixed affinity pool of unified
  relational backends, preserving single-owner queue ordering while allowing
  unrelated queues to progress on other pool members.
- The native API-001 `BatchUpdate` surface returns ordered best-effort
  per-item outcomes and executes accepted updates through one set-oriented
  PostgreSQL transaction with durable request replay.
- PostgreSQL claim candidates are materialized once before the lease update,
  preventing the `LIMIT 1` path from repeatedly evaluating the candidate scan
  as retained history grows.

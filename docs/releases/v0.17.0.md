# pqueue v0.17.0

## Highlights

- Applications can now open an owned object-log plus SQLite composition through the public facade for local or S3-compatible storage. Strict and asynchronous modes own their checkpoint lifecycle and support verification, projection deletion, and exact rehydration without deleting the authoritative log.
- The SQLite `claim_by_query` path now applies the normal eligibility rules and an atomic compare-and-set transition. Durable idempotency, conflict-first replay, renewal retention, and worker-attribution recovery now agree across the composed and SQLite paths.
- Shared object-log deployments can inject a stable per-pod owner identity independently of item node IDs, and the live E2 failover proof covers stale-owner fencing, snapshot-plus-tail recovery, and one-hop routing recovery.
- Release tooling now includes typed, revision-bound contracts for E3 evidence and governed-release manifests. These validators fail closed on incomplete matrices, stale source revisions, unsafe paths, or mismatched attestations.

## Durability and query behavior

- Embedded object-log/SQLite success remains manifest-committed and read-your-writes visible at the selected response barrier. Queue namespaces are isolated in both local and S3-compatible storage.
- Asynchronous checkpoint debt is measured per queue from real encoded bytes, age, and sealed-batch depth. A poisoned queue fails closed without preventing healthy queues behind it from making checkpoint progress.
- Query claims use the caller's deterministic eligibility time, reject leased, terminal, superseded, future, paused, gated, or changed candidates, and return only rows actually leased in declared-index order.
- Query replay survives reopen and lease renewal for the full live replay horizon; the object-log trim pin follows that renewed horizon. Lease-clearing transitions also clear persisted worker attribution before export and recovery.

## Deployment and release engineering

- The shared S3-compatible Helm profile now separates owner identity from item-placement identity and passes each pod's stable owner ID into the service.
- Host-independent E3 contract validation requires the complete two-profile, four-bound matrix, exact source revision, governed suite/backend/acceptance identifiers, structured AC-7 results, and safe canonical evidence paths.
- Governed-release helper validation supports exact-tag and semantic-version modes and rejects duplicate flags, revision mismatches, incomplete evidence, and attestation path escapes.

## Upgrade notes

- This is a backward-compatible feature release. The workspace MSRV remains Rust 1.92.
- Existing local object-log and relational deployments do not require a data migration.
- `objectlog/hybrid-strict` remains experimental through direct environment or configuration only and is not chart-selectable.

## Claim boundary

- Niflheim remained in service during this release round. The governed quiet-host 1,001-queue density diagnostic and the release-tier E3 cost plus 10-million-item recovery measurements were deliberately deferred; v0.17.0 makes no new performance claim from those rows.
- The typed governed-evidence gate is shipped and tested, but production tag-gate wiring remains open until exact release artifacts and their transport are available. The release workflow continues to enforce its existing correctness, transaction, packaging, and deployment gates.
- Dependent density, cost, and aggregate governed-evidence beads remain blocked by the deferred measurements. They were not closed with synthetic, contaminated, or smoke-tier evidence.

## Verification

- Public embedded object-log/SQLite lifecycle and object-log hybrid conformance suites pass, including strict failure/replay, request-ID conflict handling, interrupted rebuild, projection-behind recovery, and poisoned-queue isolation.
- SQLite query eligibility/CAS, reopen/replay, renewal retention, conflict precedence, and worker export/recovery regressions pass.
- Release preparation is checked with formatting, warning-denied workspace Clippy, workspace tests, DDx health/document freshness, version consistency, and the repository's release and deployment gates. Quiet-host performance commands are excluded as described above.

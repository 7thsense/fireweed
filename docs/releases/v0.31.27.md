# Fireweed Queue v0.31.27 — qualified original-row workflow performance

This release is a source-preview product pin containing the performance and
correctness changes qualified through the public API. It is not a governed
product-ready P20pr deployment evidence promotion or a remote-log performance
claim. Source artifacts include an archive, workspace-package SBOM, unsigned
source provenance, and checksums.

## Changes

- Keep each original row through load, two asynchronous enrichments, scheduled
  delivery, retries, terminal outcomes, and retention purge, using guarded
  mutations and payload-preserving metadata updates.
- Retain the projection batching, claim/mutation fusion, indexed access,
  response-delivery, and cache-accounting fixes prepared for v0.31.26.
- Use mimalloc in the workload and service executables after profiling allocation
  overhead. Library embedders retain control of their global allocator.
- Enable portable thin LTO and one codegen unit for release builds. Embedding
  applications must choose their own root Cargo profile; dependency profiles
  do not propagate. Build/link times increase by several minutes.
- Correct native automatic WAL checkpoint retries after partial backfill:
  retry against retained frames rather than postponing another full budget.
  The checkpoint budget, reader snapshot safety, and log durability are preserved.
- Qualify 32 physical shards with eight workers per shard and enforce a
  9,500 complete workflows/sec floor overall and for each cycle's slowest-shard
  equivalent rate. Primitive insertion and update floors remain 10,000/sec.

## Measured capacity

Two fresh repetitions on clean source `a73b067f`, using the same binary:

| Public API operation | Run 1 | Run 2 |
|---|---:|---:|
| Complete original-row workflows/sec | 12,125 | 11,810 |
| Worst-cycle slowest-shard equivalent workflows/sec | 9,839 | 10,036 |
| Inserts/sec | 67,738 | 67,311 |
| Enrichment updates by key/sec | 97,186 | 77,121 |
| Scheduling updates by ID/sec | 70,739 | 61,756 |
| Maximum sampled shard WAL | 259.0 MiB | 259.6 MiB |

Each workflow run recycled 500,000 recipients six times, completing three million
lifecycles including retries, failure outcomes, and purge. Each primitive run
used one million resident rows. Required throughput, exact outcomes, payload,
retention, RSS/projection stability, and sampled WAL checks passed in all four
qualification reports. The release version change preserves that production
implementation; the archived measurements retain their original source identity.

Configuration: Ryzen 7 4800H (eight cores/16 threads), 62 GiB RAM, one NVMe under
encrypted Btrfs with zstd:3, filesystem log and disk-backed Turso projections,
32 shards, eight workers per shard, four loaders, 1,000-row batches, and 8,000-row
purge batches. Enrichment handlers use deterministic compressible 1 KiB bodies.
These are batched, individually addressed row operations, not serial separately
synced requests. The finite runs are not a multi-day soak or an engine-enforced
WAL cap against arbitrarily long readers.

Validation: 106 public workload/adapter release tests passed (one existing
ignored), 77 native WAL tests passed, and four Python gate/monitor tests passed.
The new partial-checkpoint regression failed before the correction and passed
afterward. Reproduce the serial repeated qualification:

```sh
bash scripts/perf/qualify-workflow-capacity.sh /absolute/new/output-directory
```

See the [full investigation and raw evidence](../perf/workflow-9500-iteration.md)
and [hardware comparison](../perf/workflow-hardware-headroom.md).

## Compatibility

The log remains the sole durability authority. New readers support existing logs.
The payload-preserving replacement log variant introduced since the previous
published release requires an updated reader: after writing it, rollback to an
older binary lacking that variant is unsupported. Existing projection page sizes
are retained; new projections use 4 KiB pages. Vendored Turso 0.7.2 patches retain
licenses, upstream provenance, and a reviewable patch. No additional workflow
entities or Snorri interface migration are introduced.

# pqueue v0.14.0

## Highlights

- objectlog/hybrid-strict and objectlog/hybrid-async now fail closed when a recovered projection image is behind a deleted manifest prefix, and they resume from the retained floor/head replay path once the retained range is available again.

## Release Note

- Tracker audit for this release shows that the historical `pqueue-c33c367e` reference was reevaluated after dependency `pqueue-8928baec` had already closed, once the owner-fence wiring bead `pqueue-7bac12ce` landed on 2026-07-14 22:51 EDT and the restart reconciliation fix `pqueue-b29435b2` landed on 2026-07-14 23:07 EDT. That post-closure reevaluation does not change the deleted-manifest behind-image safety envelope for objectlog, `objectlog/hybrid-strict`, or `objectlog/hybrid-async`: the projection-image-behind fail-closed boundary still comes from the retained floor/head contract and permanent-head CAS, not from owner-port wiring. The physical deletion tests prove a narrower statement for objectlog recovery: deleting the legacy `manifest/` namespace alone does not break recovery, and deleting both `manifest/` and `manifest_head/` reopens conservatively with retained read-horizon state and `retention_floor=None` rather than reconstructing deleted manifest state. For repositories that have never published a durable head, recovery bootstraps from the manifest tail while that tail is still present, validates that the tail is head-compatible with the current manifest prefix, derives and publishes the first head, and only then makes head-compatible replay authoritative for later opens. Authoritative corrected release evidence for these claims is recorded in [.ddx/executions/20260715T043214-936c36b0/release-evidence-correction.md](../../.ddx/executions/20260715T043214-936c36b0/release-evidence-correction.md); the earlier failed attempt report is preserved only as superseded history.
- Branch GC on a committed branch also stays on the persisted branch metadata / source pin registry path when the source's legacy `manifest/` prefix has already been physically deleted. That leaves the inherited floor and source pin intact across GC and keeps the branch reachable from retained metadata instead of deleted legacy manifest objects.
- Branch GC now fails closed if the persisted source-pin metadata is missing or corrupt, instead of guessing through an untrusted registry entry after the source manifest prefix has been physically deleted. That keeps the cleanup path on the trusted inherited floor / source-pin record only.
- Below-floor source trim (`expire_segments_through`) now fails closed the same way: a listed-but-unfetchable source-pin registry entry for a still-committed, still-readable branch previously made `branch_pins_segment` silently treat that branch as unpinned (`read_branch_registry` skipped the entry instead of erroring), which could let a below-floor object a live branch still needs be reclaimed. `read_branch_registry` now surfaces `EngineError::Storage` on a listed-but-missing entry, matching the fail-closed contract `gc_orphaned_branches` already had, so the deletion-eligibility and read-horizon-watermark paths that consume it (`Self::expire_segments_through`, `Self::contiguous_manifest_deletion_watermark_from_entries`, `Self::lowest_branch_pinned_below`) retain the object instead of guessing. `pqueue-c33c367e` was evaluated for this change: it does not alter this conclusion — the trim path's deletion eligibility still depends only on the persisted source-pin registry / branch metadata, not on the deferred server-side `fence_epoch` wiring, so `pqueue-c33c367e` closing does not widen or narrow the retain-while-readable envelope here.
- Dependency `pqueue-8928baec` remains the governing branch-inheritance fix; the retained-floor/head and deleted-manifest evidence lives in [docs/perf/design/manifest-compaction-hotpath.md](docs/perf/design/manifest-compaction-hotpath.md) and [crates/pqueue-objectlog/tests/segmented_s3_substrate_tests.rs](crates/pqueue-objectlog/tests/segmented_s3_substrate_tests.rs).
- **SQLite propagation (bead `pqueue-073ecde6`).** The `ComposedBackend` guard (compose.rs:1782-1798) now emits the distinct `deleted_manifest_prefix_error` signal when the SQLite projection image high-water is behind the durable retention floor. The historical `pqueue-c33c367e` interaction conclusion is unchanged after `pqueue-7bac12ce` and `pqueue-b29435b2`: behind-image detection is a local consistency check on the durable floor and projection high-water, both of which remain independent of owner-port wiring. Evidence: `TestSqliteObjectlogDeletedManifestRecovery`, `TestSqliteDeletedManifestErrorPreservesGuarantees`, `TestSqlitePropagationPqueueC33c367eInteractionRecorded` in [crates/pqueue-conformance/tests/sqlite_retention_floor_source_pin_conformance.rs](../../crates/pqueue-conformance/tests/sqlite_retention_floor_source_pin_conformance.rs).
- This release-note update is documentation-only; it does not change queue semantics or user-facing APIs.
- **SQLite retained floor/head replay recovery (bead `pqueue-b9f4cd54`).** The SQLite-backed composed backend now recovers successfully from the retained floor/head after trim, without relaxing retention-floor or source-pin guarantees. Replay from the retained floor/head preserves the live tail (commands above the floor) and continues to fail closed for projection images that require physically deleted prefixes. The historical `pqueue-c33c367e` interaction conclusion is unchanged after `pqueue-7bac12ce` and `pqueue-b29435b2`: the durable retention floor is persisted in the object-log substrate independently of owner-port wiring, and the floor/head replay path never consults deleted manifest prefixes. ### Branch GC deletion proof: retain-while-readable and final-readable-branch physical deletion (bead `pqueue-c2f0b050`)

Governing artifact: [docs/perf/design/manifest-compaction-hotpath.md:374](docs/perf/design/manifest-compaction-hotpath.md) (the `ManifestHeadBlob` permanent-head contract, §6.1) and [docs/helix/03-test/test-plans/TP-003-verification-acceptance-criteria.md:224](docs/helix/03-test/test-plans/TP-003-verification-acceptance-criteria.md) (AC-TXN-4, the object-log crash-point matrix). Dependency `pqueue-8928baec` (closed) is what makes physical deletion of below-floor manifest entries possible in the first place; branch GC's deletion eligibility is the branch-aware consumer of that closed work.

- **Deletion proof.** Branch GC's below-floor source manifest/segment deletion eligibility is driven entirely by the persisted branch registry (source pins, inherited floor/head metadata, and each branch's `cut_sequence`/TTL) — never by which source manifest entries happen to still be retained. `expire_segments_through` (`crates/pqueue-objectlog/src/segmented.rs`) skips any below-floor entry a live branch still pins (`branch_pins_segment`, comparing `first_seq <= cut_sequence` against every unexpired registered branch) and only physically deletes an entry once no live branch pins it.
- **Retain-while-readable (bead `pqueue-635500fb`, closed).** With multiple committed, live branches pinning overlapping ranges of a trimmed source, below-floor source objects stay retained as long as at least one branch can still read them — proven by `TestBranchGcDeletesBelowFloorAfterLastReadableBranch` and its fail-closed counterpart `TestBranchGcDeletesBelowFloorAfterLastReadableBranchFailClosed`.
- **Final-readable-branch physical deletion (bead `pqueue-29a6c98c`, closed).** Once the last readable branch is discarded (or advances past the range), `expire_segments_through` physically removes the below-floor source manifest and segment objects — proven by `TestBranchGcDeletesBelowFloorAfterLastReadableBranchFinal` and its fail-closed counterpart `TestBranchGcDeletesBelowFloorAfterLastReadableBranchFinalConservative`.
- **Fail-closed behavior.** `read_branch_registry` surfaces `EngineError::Storage` (rather than silently skipping) when a listed branch-registry entry cannot be fetched, so a storage inconsistency during GC always retains below-floor objects instead of guessing a branch has advanced. This matches the fail-closed contract `gc_orphaned_branches` already had, and is exercised by both `...FailClosed` tests above.
- **Historical `pqueue-c33c367e` interaction: evaluated, no effect on the rollout safety envelope.** `ddx bead show pqueue-c33c367e` now returns `bead: not found`; the tracker audit for this release follows that historical reference through `pqueue-7bac12ce` and `pqueue-b29435b2`. The conclusion recorded at [docs/perf/design/manifest-compaction-hotpath.md:388](docs/perf/design/manifest-compaction-hotpath.md) is the narrow release gate this bead needed: the index-CAS fence requires below-floor manifest addresses to remain occupied, so owner-fence wiring and restart reconciliation do not change the deleted-manifest rollout safety envelope. The branch-GC claims in this section remain grounded in the persisted source-pin/branch registry behavior and the named branch-GC tests below, not in the owner-port wiring.
- **Operational justification.** This deletion path is worth the added branch-registry bookkeeping only for very long-lived, high-write, trimming-enabled queues where manifest object-count and storage growth from never-freed below-floor addresses is operationally real; a queue that trims rarely or is short-lived does not need it and should not treat this as a required upgrade path.
- **Review.** Codex adversarial review for this release-note gate must be recorded by resolved findings and their validating evidence, not by transport behavior. The final review outcome and any follow-up fixes are recorded in the verification matrix below alongside the release-gate commands.

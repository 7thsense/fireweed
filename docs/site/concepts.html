Technical concepts

The product contract in scannable form: lifecycle, eligibility, leases, transaction integrity, and storage composition.

Work item lifecycle

Items are inserted, ordered by priority, claimed under a lease by a worker, then settled in one atomic commit with a Disposition: Complete, Fail, Release, RetryAt, Retain or Delete. A commit can also change state records and insert new work in the same step.

Example: basic lifecycle · Rust API

Priority vs eligibility

Priority ranks eligible work. Eligibility decides whether an item may be claimed at all: available_at, active leases, and retry times.

Example: scheduled delivery and retry

Leases and recovery

A claim grants temporary exclusive execution authority. A lease that expires returns the item to pending so another worker can continue; a commit with a stale lease is rejected.

Filters, indexes and state

A queue schema declares typed fields and indexes. Claims, queries and stats select by filter over those fields; state collections hold per-key records that commit atomically with work.

External transaction contract

On supported durable profiles: a successful mutation is durable and visible; a rejected mutation has no durable effect; unknown outcomes are resolved by retained request_id replay (same body → same result; different body → RequestIdConflict).

Architecture

Queue sits on a shared engine. The production backend composes an S3 command log, a disposable local Turso projection and PostgreSQL queue leases.

Out of scope

  • Workflow DAGs and multi-step graph engines
  • Broadcast event buses and multi consumer-group fan-out of one item
  • Using the internal change log as an application event stream
  • Downstream API rate admission as a core Fireweed feature

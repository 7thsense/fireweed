Get started

Fireweed v0.22.0 is a source public preview. Clone the repository; crates.io and GHCR publication are deferred.

Prerequisites: Git, rustup, a C toolchain and CMake for native crypto dependencies. The memory backend is disposable and development-only.

Path A — embed Rust

clone and exercise the facadesh
git clone https://github.com/7thsense/fireweed.git
cd fireweed
# Requires rustup; toolchain from rust-toolchain.toml (Rust 1.92.0)
cargo test -p fireweed --test concrete_fireweed
cargo run -p fireweed --example scheduler_boundary

The public root type is concrete Fireweed. The normative full-matrix entry is typed StorageConfig with open / open_async—any of the five log backends (memory, sqlite, postgres, filesystem, s3) paired with any of the three projections (memory, sqlite, postgres). Convenience helpers (open_memory, open_sqlite, open_objectlog, …) map onto the same surface for common cells. Walk basic lifecycle then scheduler boundary.

Path B — Redis-shaped workers

build the RESP servicesh
# From repository root after building fireweed-service
# See README Quickstart for the in-memory RESP path with redis-cli.
cargo build -p fireweed-server
# Follow README for XADD / XREADGROUP / XACK against the local service.

Stock Streams worker commands map onto Fireweed claim/finalize semantics. See the README quickstart for a full redis-cli session, and the RESP drain example extracted from e2e tests.

Worked Python queue-management scenarios (docs + e2e + optional performance) live in the repository at examples/python-resp/ (run_e2e.py, run_perf.py).

### Findings

| Severity | Area | Finding |
|---|---|---|
| BLOCKING | live ≠ rebuild | The plan removes pre-claim tail-apply ("Claim … Do **not** wait for apply of this claim or of previous completes") *and* makes update-apply skip `Leased` rows (cut 2). Together these break log-replay equivalence. `class_s_claim` writes the lease directly to `fireweed_items` (`crates/fireweed-relational/src/claim.rs:139-155`) at wall-clock time, i.e. **out of log order**. A `BatchUpdate` appended at position P1 and a `Claim` at P2: live applies the lease first, then skips the update; rebuild replays P1 against a still-`Pending` row and applies it. Divergent rows, silently. `one-projection-cleanup.md` §2 required "apply this queue's unapplied log tail so the `Claim` is the next position (live == rebuild)" — that is exactly the line this plan deletes, and it is not replaced. No "Done when" item tests rebuild == live. |
| BLOCKING | push validation | "Push / update plan: `SELECT` on the reader. Keys exist or they do not" is not what `validate_push` checks. `projection.rs:3897-3925` also rejects on `item_id` collision, on `fireweed_item_key_retention.expires_at > now` (tombstone window), and on `superseded`; `projection.rs:3932` enforces `max_eligible_group_size` — and that cap is enforced **nowhere in apply** (only hit at 3932). Planning off a stale reader with no tail-apply means concurrent/unapplied pushes silently exceed `max_eligible_group_size` and can reuse a key inside its retention window. The plan only discusses duplicate `client_item_key`. |
| BLOCKING | push contract | "Apply of the second push **skips** the duplicate key" changes a synchronous client error into a silent drop. Today the duplicate is `EngineError::Conflict` from `validate_push` (`projection.rs:3925`). Under the plan the second push is **acked**, returns `item_ids`, and then never materializes — `live_item` on those ids returns nothing, forever. The plan does not say what the client sees, which row wins, whether `fireweed_request_idempotency` records the drop, or whether a counter/log exists. Undefined durable semantics for an acked write. |
| BLOCKING | live_tokens | "`live_tokens` is a leftover process HashMap written after every claim. Delete it." It is not leftover — it is the **only** serving authority for the entire pending/lease read surface on Turso: `server_pending` (`projection.rs:3606`), `server_pending_summary` (3628), `server_pending_by_ids` (3689), `server_pending_page` (3712), `server_pending_range` incl. the consumer filter (3741, 3752). Those loops `continue` when the token is missing, so deleting the map returns **empty lists, not errors** — a silent API regression. Same shape in `fireweed-sqlite` (`backend.rs:898-977`, `query.rs:886-1015`, and `item.lease_token` at `backend.rs:1376`). This is a query-layer migration onto `fireweed_lease_bearers`, not a delete, and cut 1 schedules it as a delete. |

Delete `live_tokens` and that path's leases become unqueryable until apply lands. |
| BLOCKING | outbox / durability | The claim row ends at "append the claim to the object log." Missing every durability rule the governing doc mandates: retry-the-same-envelope until PUT is durable, delete the outbox row only then, drain the outbox on open, and do not run another Class S `SELECT` on that queue until log and projection agree. Current code deletes the outbox row after append (`turso_compose.rs:1913`) and on append error returns `Err` with the lease already committed and no reconcile (`turso_compose.rs:1886-1895`). "Done when" has no kill-after-commit-before-PUT test, though the governing doc requires one. Consequence: a lost PUT leaves rows leased with no log record → rebuild shows them `Pending` → double lease. |
| BLOCKING | group summaries | Cut 2 says "Drop group-summary refresh from item-level claim apply" and stops there. `one-projection-cleanup.md` §4 required both halves: "skip on item-level claim **and refresh on grouped read**." Grouped/cohort eligibility reads `fireweed_group_summary` inside the writer txn (`projection.rs:1065`, `1149`); with no refresh-on-read, grouped claim decides on stale summaries. Half a rule shipped as a whole one. |
| BLOCKING | claim scope | The plan describes one claim shape. `SELECT_CLASS_S_DUE` explicitly excludes cohorts (`claim.rs:14`, `cohort_size IS NULL`) and applies no group-exclusivity predicate, so whole-group / whole-cohort / expired-lease reclaim / reassign still run the racy legacy choose-then-log path — which `one-projection-cleanup.md` classifies as Class S. The gate "Claim does not call `catch_up_projection`" is ambiguous about whether those paths are in scope, and two implementers will read it differently. |
| BLOCKING | reader lifecycle | "Route plan/validate/`live_item`/pending/metrics through `connect()`" — `connect()` builds a **new** connection per call (`local.rs:275-279`) and runs `configure_connection`: four pragma round-trips plus `busy_timeout` (`local.rs:648-661`). Per-read connection setup can cost more than the writer lock it replaces. The plan never says shared/pooled, which the governing doc did ("One shared reader connection is enough"). |

### Verdict: REQUEST_CHANGES

### Summary

The direction is genuinely "just use SQL" and is correct: reads on a second connection, a short lease txn, and no wait for an apply tail nobody needs. But two of the plan's own line items are not that — deleting `live_tokens` is a migration of five serving queries onto `fireweed_lease_bearers`, and "skip duplicates / skip leased at apply" is a change to durable semantics, not a lock change. The load-bearing problem is that the plan deletes the pre-claim tail-apply without replacing what it bought: log-order equivalence (live == rebuild), the push checks that only `validate_push` enforces (`max_eligible_group_size`, key retention, item-id collision), and a synchronous duplicate-key error. That is where a workaround grows back, and it is the honest form of the "then we discuss a table" escape hatch — the plan should decide those semantics now, not discover them at N=100k. Fix the eight BLOCKING items in the spec (they are spec text, not extra cuts), correct the push diagnosis before cut 1 so cut 3's gate can actually be met, and this stays three cuts.

The sound cursor already exists — `wait_for_catch_up` (`async_projection_apply.rs:380-392`), whose depth counts `Reserved` entries (`debt_for`, `:665-688`) — but it blocks on *every* in-flight reservation including other claims and completes, i.e. exactly the per-claim waiting Cut 3 forbids. It also puts a group aggregate back inside the claim's write txn, contradicting "lease+append, p50 in the ingest band." |

### Verdict: BLOCK

### Summary
Cut 1 is not implementable as written without lying on `BatchUpdateOutcome` — every field of `Updated` is required and the plan supplies none of them for a miss, mis-reports `item_version` even on hits, and silently voids `expected_item_version`; the command change is left as the phrase "keep `item_id` for old envelopes," which is not a wire design. The Class S seam is specified against `last_produce`, a cursor published *after* append while apply slots are reserved *before* it, so a concurrent produce can be leased over — and the only sound cursor in the tree, `wait_for_catch_up`, is precisely the per-claim wait Cut 3 forbids; that tension is the plan's central unsolved problem, not a detail. Cut 2 is worse than incomplete: the rerank rule is wrong whenever the representative moves to an unchanged member (the normal case at SS's group fan-out), and removing claim-apply's group maintenance is a live≠rebuild divergence. Finally, the deliver target: Cut 1 does not delete P2/P3's apply cost, it defers it into P4's seam, which sits inside P4's wall clock — so "deliver ≥ ingest" requires ~60 k row-mutations/s plus 200 IMMEDIATE txns through one Turso writer in 0.327 s, a budget the plan never names.

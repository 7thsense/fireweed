### Findings

| Severity | Area | Finding |
|---|---|---|
| BLOCKING | Apply wait | The Push/Update wait is not implementable from the current coordinator state without adding new coordinator metadata/API. The draft relies on “already-queued envelopes” ([plan](/home/erik/Projects/fireweed/docs/helix/04-build/writer-contention-recovery-plan.md:56)), but `Reserved` entries store only counts/debt, not commands or positions ([async_projection_apply.rs](/home/erik/Projects/fireweed/crates/fireweed-objectlog/src/async_projection_apply.rs:77)). Commands appear only later in `Ready(ApplyBatch)` ([async_projection_apply.rs](/home/erik/Projects/fireweed/crates/fireweed-objectlog/src/async_projection_apply.rs:125)), after `packed_append` and `enqueue_reserved` ([turso_compose.rs](/home/erik/Projects/fireweed/crates/fireweed/src/turso_compose.rs:1320)). A claim can enter during append-before-enqueue and miss an earlier Push/Update. The only existing wait is whole-shard depth zero ([async_projection_apply.rs](/home/erik/Projects/fireweed/crates/fireweed-objectlog/src/async_projection_apply.rs:362)), which reintroduces waits for unrelated Complete despite the draft forbidding that ([plan](/home/erik/Projects/fireweed/docs/helix/04-build/writer-contention-recovery-plan.md:48)). |
| BLOCKING | Claim fallback | The UPDATE-then-SELECT fallback is exclusive against a second claim only if it stays inside the same writer transaction, which the Turso path does via writer mutex plus `BEGIN IMMEDIATE` ([local.rs](/home/erik/Projects/fireweed/crates/fireweed-turso/src/local.rs:333)). But “SELECT ... by `lease_token_hash`” is not enough identity for “just leased” rows ([plan](/home/erik/Projects/fireweed/docs/helix/04-build/writer-contention-recovery-plan.md:40)). `LeaseToken` is only validated non-empty ([domain.rs](/home/erik/Projects/fireweed/crates/fireweed-core/src/domain.rs:31)), `ClaimRequest` carries a token supplied to the port ([port.rs](/home/erik/Projects/fireweed/crates/fireweed-engine/src/port.rs:674)), and the item schema has no uniqueness on `lease_token_hash` ([schema.rs](/home/erik/Projects/fireweed/crates/fireweed-relational/src/schema.rs:15)). Existing hash lookup helpers scope by explicit item ids, not hash alone ([apply.rs](/home/erik/Projects/fireweed/crates/fireweed-relational/src/apply.rs:1083)). |
| BLOCKING | Performance gate | The 90% produce target is not justified under shared-core Turso apply/log PUT contention. The draft makes `filesystem--memory` the control and requires `filesystem--turso` produce to hit 90% ([plan](/home/erik/Projects/fireweed/docs/helix/04-build/writer-contention-recovery-plan.md:86)), while also including apply drain in wall time ([plan](/home/erik/Projects/fireweed/docs/helix/04-build/writer-contention-recovery-plan.md:90)). But async commits still reserve/apply-debt before append ([async_projection_apply.rs](/home/erik/Projects/fireweed/crates/fireweed-objectlog/src/async_projection_apply.rs:179)), enqueue Turso apply after log append ([turso_compose.rs](/home/erik/Projects/fireweed/crates/fireweed/src/turso_compose.rs:1342)), and return before apply only when async apply is enabled ([turso_compose.rs](/home/erik/Projects/fireweed/crates/fireweed/src/turso_compose.rs:1369)). If apply and PUT share a core, apply CPU is part of the measured cost, so “log is the bound” is an assumption, not an acceptance criterion. |
| NOTE | Lease exclusivity | The second-claim TOCTOU itself is covered by the intended transaction shape: current Class S claim takes the single Turso writer lock and opens an immediate transaction before mutating leases ([local.rs](/home/erik/Projects/fireweed/crates/fireweed-turso/src/local.rs:338)). The remaining issue is the fallback selector’s identity, not two writers leasing the same row concurrently. |

### Verdict: BLOCK

### Summary
The draft fixed the wording around “one writer transaction,” but the coordinator wait still has an observability gap: reserved/appended-but-not-enqueued Push/Update commands are not inspectable as “already-queued envelopes.” The fallback lease mutation can be exclusive, but the hash-only re-read is under-specified and can over-select rows if tokens repeat. The 90% performance gate also needs a resource model or revised bound for shared-core apply/log contention.

### Findings

| BLOCKING | Claim catch-up | Dropping claim catch-up breaks live == rebuild for prior durable updates. The plan says no `catch_up_projection` and claims unapplied push/update rows are “not `Pending` with payloads” ([plan:19](/home/erik/Projects/fireweed/docs/helix/04-build/writer-contention-recovery-plan.md:19), [plan:54](/home/erik/Projects/fireweed/docs/helix/04-build/writer-contention-recovery-plan.md:54)), but an unapplied `BatchUpdate` can target an existing Pending row. If claim leases it first and apply then skips `Leased` updates ([plan:72](/home/erik/Projects/fireweed/docs/helix/04-build/writer-contention-recovery-plan.md:72)), live skips the update while rebuild applies update before claim. |
| BLOCKING | One-shot spec | “One SQL statement” is ambiguous. The lease can be one `UPDATE ... RETURNING`, but the plan also requires bearer rows and outbox inserts in the same txn ([plan:34](/home/erik/Projects/fireweed/docs/helix/04-build/writer-contention-recovery-plan.md:34), [plan:48](/home/erik/Projects/fireweed/docs/helix/04-build/writer-contention-recovery-plan.md:48), [plan:91](/home/erik/Projects/fireweed/docs/helix/04-build/writer-contention-recovery-plan.md:91)). Current `class_s_claim` is still SELECT then UPDATE then bearer/outbox writes ([claim.rs:95](/home/erik/Projects/fireweed/crates/fireweed-relational/src/claim.rs:95), [claim.rs:137](/home/erik/Projects/fireweed/crates/fireweed-relational/src/claim.rs:137), [claim.rs:163](/home/erik/Projects/fireweed/crates/fireweed-relational/src/claim.rs:163)). Two implementers can both claim compliance while building different pipelines. |
| BLOCKING | Token authority | `fireweed_lease_bearers` is a second token store unless explicitly defined as a derived index with complete transition rules. The plan routes pending through bearers ([plan:77](/home/erik/Projects/fireweed/docs/helix/04-build/writer-contention-recovery-plan.md:77)), while the governing cleanup says the item row keeps only the hash and the outbox holds the full envelope, “Do not put bearer tokens on every leased row” ([cleanup:119](/home/erik/Projects/fireweed/docs/helix/04-build/one-projection-cleanup.md:119)). RETURNING` ([plan:56](/home/erik/Projects/fireweed/docs/helix/04-build/writer-contention-recovery-plan.md:56)). SQLite 3.53 accepted the shape locally, but the repo pins `turso = 0.7.0` ([Cargo.toml:25](/home/erik/Projects/fireweed/crates/fireweed-turso/Cargo.toml:25)) and existing Turso claim code does not exercise `RETURNING`. ### Verdict: BLOCK

### Summary

This is not one SQL shot end-to-end. At best, the lease selection/update can become one SQL statement; the claim path is still a transaction plus bearer/outbox writes plus log PUT/retry/drain. Dropping catch-up before claim is unsafe as drafted because durable updates can be skipped in live state but applied during rebuild. The Turso statement shape and 90% gate also need concrete probes before this can be implemented consistently.

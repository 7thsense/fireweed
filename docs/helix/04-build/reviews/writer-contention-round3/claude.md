## Findings

| Severity | Area | Finding |
|---|---|---|
| BLOCKING | Dropping catch-up (Q2) | The plan's whole justification for removing `catch_up_projection` is false for updates. Plan §Claim: *"Unapplied push/update rows are not `Pending` with payloads yet, so they are not selected."* True for a push (row absent), **false for a `BatchUpdate`**: the row is already `Pending` with payloads in SQL; only the *mutation* is unapplied. The plan's own apply rule at §Apply (*"Update of `Leased`: skip that row"*) exists precisely because such a row can be claimed. Sequence: log pos 100 = `BatchUpdate(X)` unapplied; Class S commits the lease and appends `Claim(X)` at 101. Live: worker gets payload v1, then pos 100 applies and is skipped → X stays v1. Rebuild: 100 applies (v2 / new `not_before`), then 101 leases X at v2. Live ≠ rebuild, and a worker was handed a payload the log says was superseded. The catch-up prefix was the thing that made the `Claim` "the next position (live == rebuild)" (`one-projection-cleanup.md` §Class S). |
| BLOCKING | Projection is no longer a log prefix (Q2) | With no catch-up, the committed projection is `prefix(cursor N) + one command at position N+k`. That is not any prefix of the log. `recovery_high_water` (`turso_compose.rs:1541-1548`) still reports N, so a Strict waiter is told "applied through N" while rows already carry lease state written by a command at N+k. The plan never states what invariant replaces "live == rebuild", so the differential/recovery suites have no defined expectation. |
| BLOCKING | Produce reader TOCTOU (Q1) | Cut 2 makes `validate_push` a reader `SELECT` and simultaneously bans both governing-doc mitigations (§20 "No `catch_up_projection` on claim or **produce**"; §Not this plan "reservation table"). `one-projection-cleanup.md` §3 required *one of* apply-the-tail or a SQL reservation table. The plan's replacement (§Produce: *"If the reader cannot see a key or request-id that is still sitting in the apply queue, wait for those apply positions"*) is circular and unimplementable: the reader cannot know an invisible key is in the apply queue without either an in-process unapplied-key set (forbidden by the same plan) or scanning the unapplied log tail (which is catch-up by another name). Result: two pushes of the same `client_item_key` both validate, both reach the log, and apply "skips the row" after the client got an ack — the exact silent-drop the plan says at §Produce it will not do (*"Do not ack a push and later drop the row"*). Today's `IMMEDIATE` txn (`projection.rs:3864-3870`) is not "a write txn that only rolls back"; it serializes that check against the writer. |
| BLOCKING | `RETURNING` on Turso is unverified, and so is the fallback (Q3) | There is **zero** `RETURNING` in any Turso code path — every hit is `fireweed-postgres` or `fireweed-sqlite` (rg over `crates/`). `turso = "=0.7.0"` is pinned, and the repo's own capability gate, `docs/helix/00-discover/turso-0.7-compatibility-probe-results.md`, probed schema, PRAGMA, anti-join/CTE, WAL checkpoint, 16 writers — and never `RETURNING`, never `UPDATE … WHERE id IN (SELECT … LIMIT n)`, never a correlated gate anti-join *inside* an UPDATE subquery. The plan's fallback (§Claim: *"If Turso cannot `UPDATE…RETURNING` that subquery, keep one txn with a single `WITH … UPDATE … RETURNING`"*) depends on the same unproven feature, so there is no fallback at all. This must be a probe result recorded before Cut 1 is scheduled, with a stated non-`RETURNING` path (`UPDATE` + re-`SELECT` by the just-written token hash in the same txn) if the probe fails. |
| BLOCKING | Claim ordering lost (Q1) | The plan's `RETURNING /* payloads and lease fields */` returns rows in unspecified order and drops the sort keys. Postgres shipped a bug fix for exactly this (`docs/releases/v0.19.2.md`, `v0.19.3.md`) and now asserts it: `relational.rs:11444` — *"UPDATE RETURNING order is unspecified; claim responses MUST restore queue order"* — which is why `CLAIM_CTE` returns `claim_priority_sort, claim_created_seq` and wraps the CTE in an ordered outer `SELECT` (`relational.rs:802-808`). SQLite/Turso **cannot** select from a data-modifying CTE, so the outer `ORDER BY` is unavailable; the returned columns must carry `priority_sort`/`created_seq` and the adapter must re-sort client-side. `ClassSClaimedItem` (`claim.rs:52-68`) carries neither. As written, priority/FIFO order is silently dropped on Turso. |
| BLOCKING | Second claim path untouched | `turso_compose.rs:1762-1766`: any claim with non-default `ClaimCompatibility` (`group_key`, `same_group_key`, `metadata_equals`, `group_batching`, `whole_cohort` — `claim_validation.rs:33-39`) routes to `dispatch_claim_legacy` → `prepare_claim` + `commit_prepared`, i.e. choose-then-log with no projection lease. `one-projection-cleanup.md` §Class S names "whole-group / whole-cohort claim" as Class S. The plan never mentions this path, and its only exclusivity test ("Two `claim(100)` never share ids") exercises only the default path. Grouped/cohort claims keep the race the plan exists to kill. |
| BLOCKING | Post-COMMIT failure has no contract | §Claim says only *"Retry the same envelope until durable… Do not unlease."* The governing doc required classification (`one-projection-cleanup.md` §2: I/O → retry; `EpochFenced`/backpressure/poison → queue claim-blocked, named repair; *"Gate `reserve()` **before** `BEGIN`"*). The plan never mentions `reserve()`, epoch, or `EpochFenced`. Two consequences: (a) reserve order is undefined, and if an implementer puts `reserve()` after the txn, a `Backpressure` rejection (`async_projection_apply.rs:194-222`) leaves rows leased with no log record; (b) under `EpochFenced` "retry until durable" never terminates — the log is owned elsewhere — so the queue is permanently claim-blocked with no named repair. Today's code reads the epoch *before* the SQL txn (`turso_compose.rs:1771-1775`) and simply returns `Err` after leasing. |
| WARNING | Measurement moved, not eliminated (Q4) | `metrics()` still catches up (`turso_compose.rs:1230-1238`), and the harness captures P4's wall clock **before** calling `metrics()` (`ss_phased_capacity.rs:743-756`, then `assert_eq!(metrics.complete, n)`). Today the apply drain is amortized inside P4 because claim catches up (`turso_compose.rs:1770`). After Cut 1 the drain lands outside every measured phase. The phase throughputs will rise against the `115/73/73/86` baseline partly by relocating work past the measurement boundary. The plan must require end-to-end wall (including drain to `complete == n`) or the 90% line measures nothing. |
| WARNING | Second control does not exist (Q4) | `SS_CELL` accepts only `objectlog` / `objectlog-turso` / `sqlite` (`ss_phased_capacity.rs:122-193`). "Turso writer: isolated apply of the same packed batches (no plan on the writer)" is not a mode anyone can run, and the plan does not schedule building it. Half the target is currently unmeasurable. |
| WARNING | 90%-of-min may be unattainable by construction (Q4) | The two controls each isolate one of two resources the real run uses **together**. If log PUT and Turso writer serialize at all, combined throughput is bounded well below `min(A,B)` — two equal 100/s stages fully serialized cap at 50/s, i.e. 50% of min, with zero waste to cut. The plan gives no overlap argument and no exit ("profile, cut, re-measure. **Repeat until** the 90% line holds"). Define the target as a ratio you can argue is reachable, or bound the iteration. Also missing: repeat count, variance, host pinning, and the definition of "does not collapse vs 10k". |
| WARNING | "One statement" is one transaction with ≥4 statements plus a pipeline | Even after collapsing pick+lease: gate keys need a separate `SELECT` (`claim.rs:191+ load_class_s_gate_keys`; they live in `fireweed_item_gates` and cannot come from `RETURNING`), bearers need an `INSERT` (`claim.rs:163-180`), outbox needs an `INSERT` (`claim.rs:181-198`). Then `delete_claim_outbox_row` is a **second writer acquisition** per claim (`turso_compose.rs:1911-1917`), plus `packed_append`, `enqueue_reserved`, and `remember_leases`. State the invariant you actually want — "pick and lease are atomic; exactly one writer acquisition before the append" — because "one SQL statement" (§Cuts 1) will be read literally and will not survive gate keys. |
| WARNING | Reader probe gate deleted | `one-projection-cleanup.md` §1: *"**Gate before anything else:** probe Turso 0.7 — hold an `IMMEDIATE` writer txn on connection A, `SELECT` on connection B"*, including `:memory:` and file, WAL truncate with a reader open. Cut 2 just asserts the reader works. `local.rs:284-288` `connect()` is documented as "for future read-side fan-out" and is unused; nothing in the repo shows whether B blocks, returns pre-txn rows, or (for `TursoConfig::in_memory()`, used by most tests) even sees the same database. If B blocks on the writer, Cut 2 is a no-op and the plan's stated cause of slowness is unfixed. |
| WARNING | Claim request-id replay dropped | `ClassSClaimRequest` carries `request_id`/`request_fingerprint` (`claim.rs:43-44`) and the outbox persists them, but `class_s_claim` never consults `fireweed_request_idempotency` (Postgres has `IDEMPOTENCY_OPERATION_CLAIM_BY_QUERY`, `relational.rs:~773`). §Claim covers "kill after COMMIT before PUT" but not "PUT durable, client never heard" — which the governing doc did (*"retry with request-id / token replay"*). As written, the retry leases a **different** set and the first set stays leased to a token nobody holds until expiry. |
| WARNING | Expired-lease reclaim / reassign unclassified | The governing doc makes expired-lease reclaim and reassign Class S ("anything that selects from a contended set"). The plan does not mention them in §Claim, §Apply, or §Not this plan. Two implementers will split on whether the reclaim sweep gets the one-shot treatment or stays log-then-apply. |
| NOTE | Bearer tokens | `fireweed_lease_bearers` stores the **plaintext** `lease_token` per leased item (`claim.rs:163-180`, `schema.rs:283-291`) while the item row stores only `lease_hash(...)`. §Apply promotes this table to the pending-listing authority. Reconcile with `one-projection-cleanup.md` (*"The item row keeps `lease_token_hash` only… Do not put bearer tokens on every leased row"*) or state explicitly that the hash-only property is scoped to `fireweed_items`. |
| NOTE | Elided predicates | The plan's SQL elides the eligibility set with `...`. The real predicate includes `superseded=0`, `cohort_size IS NULL`, `eligible_since IS NOT NULL`, and the gate anti-join (`claim.rs:12-19` `SELECT_CLASS_S_DUE`). Spell it out; the gate `NOT EXISTS` correlated to the UPDATE target inside an `IN (SELECT … LIMIT)` is the least likely construct to survive Turso. |
| NOTE | Control mislabeled | `filesystem--memory` is labeled "Object-log packing"; it also runs the full in-memory projection. It is an upper bound on the log-only cost, which makes the target easier, not harder — but say so rather than calling it the packing bound. |

## Verdict: BLOCK

## Summary

It is not one shot. It is one *transaction* containing at least four statements (lease, gate keys, bearers, outbox), followed by a second writer acquisition to delete the outbox row, then append, enqueue, and `remember_leases` — so the "outbox/bearers/log pipeline" the review question asks about survives intact, and only the pick+lease TOCTOU is actually collapsed. The central mechanism is unverified: there is no `RETURNING` anywhere in the Turso adapter and the repo's own compatibility probe never tested it, while the plan's stated fallback depends on the same feature. Dropping `catch_up_projection` is not safe as argued: the "unapplied rows are not Pending yet" premise holds for pushes and fails for updates to rows that are already Pending — contradicted by the plan's own "Update of `Leased`: skip that row" rule — which breaks live == rebuild and leaves the projection in a state that is no prefix of the log. Fix the false premise, record a Turso `RETURNING` + reader probe before scheduling Cut 1, define reserve/epoch/PUT-failure ordering, restore queue ordering to the returned rows, say what happens to the legacy grouped/cohort claim path, and make the 90% target include the apply drain and a control that exists.

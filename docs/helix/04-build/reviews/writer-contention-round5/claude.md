| BLOCKING | Produce cursor scope | The cursor does not establish the invariant it is introduced for (`plan:50` "live == rebuild"). It observes *appended* produces only, and nothing serializes an in-flight produce against a claim. `batch_update` takes **no** queue permit at all (`turso_compose.rs:757-840`; `reserve_planned_updates` is `Ok(None)` at `turso_compose.rs:1587-1593` and `:257-263`), and push/claim explicitly **release** the permit before append (`async_composed.rs:867-871`, `:1880-1883`). Both then go through `packed_append` with a 20 ms linger (`log_engine_store.rs:126`). So a `BatchUpdate` that is planned-but-not-yet-appended when claim reads `last_produce` can seal at a position *below* the claim's: log order is update→claim, live order was claim→update, and apply then skips the update on a `Leased` row (`plan:70`). Divergent. Note this hole is **pre-existing** — today's `catch_up_projection` (`turso_compose.rs:1530-1553`) waits on the tail *as of the call* and has the same window — so this is not a regression. The defect is that the plan asserts a guarantee the mechanism doesn't deliver, and the named test ("rebuild matches live after update-then-claim", `plan:114`) is sequential and will pass either way. Fix is either a scope sentence ("closes appended-but-unapplied; concurrent in-flight produce stays as today") or a real produce gate — but "Not this plan" (`plan:101`) currently rules out the gate. |
| WARNING | Measurement accounting | `plan:92` requires drain-to-`complete == n` inside the wall. The harness captures `wall: t0.elapsed()` at `ss_phased_capacity.rs:747` **before** the `complete == n` assertion at `:755`, so drain is outside the wall today — for every phase, not just P4. Worse for the hard gate: P1–P3 return after append under async apply, so the ≥90%/≥50% produce gate (`plan:90`) is satisfiable by deferring apply debt into P4. The plan forbids exactly this for deliver but not for produce. No cut lists the harness change. (I am not re-opening the 90%/50% numbers — this is the accounting under them.) |

## Verdict: BLOCK

## Summary

The three round-4 folds are individually sound and I am not re-opening them — the produce cursor is implementable and nearly free (`catch_up_projection` already has the exact loop shape), the RETURNING fallback at `plan:40` matches the existing same-txn `SELECT`→`UPDATE`→bearers→outbox code in `claim.rs:97-199`, and the 90%/50% gate is a reasonable target. Two things block: Cut 0 (`plan:78`) still instructs the implementer to choose the hash-only selector that `plan:40` forbids, and the produce cursor is presented as establishing `live == rebuild` when it only covers produces that already hold a log position — `batch_update` holds no permit and push/claim release theirs before a 20 ms-linger append, so the plan→append window stays open. That window is pre-existing, not introduced here, so the honest fix may be a scope sentence rather than new machinery; but the plan currently claims the guarantee and the named test won't catch the difference. Fix those two and the WARNINGs (drain outside the wall at `ss_phased_capacity.rs:747`, missing outbox epoch, monotonic `max`, Done-when gate) and this is ready to cut.

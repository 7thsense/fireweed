I read the plan, both discover notes, API-003, the PRD scale-substantiation section, and traced the actual code paths in `fireweed-projection` and the facade. Findings below.

### Findings

| Severity | Area | Finding |
|---|---|---|
| BLOCKING | Wrong layer / claim selection | **The binding cost for P2–P4 is claim selection, which no slice touches.** `select_item_claim` (`crates/fireweed-projection/src/compose_impls.rs:578-607`) takes the `metadata_equals` branch whenever a predicate is present and calls `projection.eligible_candidates(now, usize::MAX)`. That resolves to `strict_candidates(now, usize::MAX)` (`lib.rs:427-437`), which iterates the **entire** eligible set, applies `due_at` per key, and `collect()`s it into a `Vec<ItemId>` — *before* any filtering. The benchmark mandates `metadata_equals` on P2/P3/P4 (`seventh-sense-phased-capacity-benchmark.md` §"Phase token"), so at N=1M every one of the ~10⁴ claims per phase materializes a 10⁶-element Vec. That is ~10¹⁰ element writes per phase in candidate materialization alone. **G1 (P4 ≥ 50k) needs 2 ms/claim; building that Vec is 10–30 ms/claim.** Plan §Diagnosis lists five per-item encode/apply costs and never mentions this line. I0–I6 cannot move G1 or G2. |
| BLOCKING | Wrong layer / quadratic P2-P3 | **P2/P3 are additionally O(N²).** `transition` re-inserts a released item with its unchanged `priority`/`created_seq` (`lib.rs:2092-2094, 2121-2123`), so a `release`d item returns to its **original** position at the head of the eligible order. Claim *k* of P2 must skip the 100(k−1) already-enriched items before reaching unprocessed work: Σ ≈ 5×10⁹ record lookups for N=1M. This is intrinsic to the "pull 100, amend, put back" shape the discover spec calls the default. G2 ≥ 30,000 items/s is unreachable by any amount of `insert_pending` tuning. It also violates the upstream model this plan depends on: `first-principles-performance-model.md` §3 — "Claim selection must stay O(log n) at 10M resident items; a scan is a 100 ms–class failure." |
| BLOCKING | I0 not implementable | **The public `BatchUpdate` cannot update a leased item, so the P2/P3 loop as specified does not exist.** `batch_update_preflight` rejects any record where `record.state != ItemState::Pending` (`crates/fireweed-projection/src/lib.rs:4026-4033`); the facade doc says "pending, non-leased … leased entries return `Conflict`" (`crates/fireweed/src/lib.rs:5210-5219`); API-003 Producer obligation 5 says "`BatchUpdate` applies to pending items only." The benchmark's P2 is claim → `BatchUpdate` those ids **under the lease** → `release`. The plan's own Non-goals asserts "RESP cannot express lease-scoped `BatchUpdate` + `release`", implying the native facade can — it cannot. The only leased-legal write is `Fireweed::update_fields`, one item per call (`crates/fireweed/src/lib.rs:5182`, permitted by `update_fields_validate` at `lib.rs:4253-4267`). That makes P2 **1 claim + 100 update commits + 1 release per 100 items**, not the "three public commits per 100 items" the discover spec prices. G2/G3 are derived from a cost model the API cannot deliver. |
| BLOCKING | I2 / claim echo | **I2 breaks claim echo on the exact target cell.** Plan I2: "Claim/render still echoes via `echo_entity_document` at read time (v0.31.0 contract)." False for `open_sqlite`. `open_sqlite` (`crates/fireweed/src/lib.rs:6485`) composes `SqliteLog` + `InMemoryProjection`; that projection's `to_claimed` returns `entity: self.entity_document.clone()` (`fireweed-projection/src/lib.rs:265`) with **no** read-time echo. `echo_entity_document` is called at read time only in `fireweed-sqlite/src/relational/query.rs:1139`, `fireweed-postgres/src/relational.rs:4599`, `fireweed-turso/src/projection.rs:4651` — none on this path. Deleting the `rehydrate_entity_document` call at `lib.rs:1970` returns `entity: null` for index-fields-only pushes. I2's In-scope list does not include adding read-time echo to `fireweed-projection`. |
| BLOCKING | I2 / unique indexes | **I2 silently disables unique-index enforcement on the update path.** `index_validate_with_entity` passes a hardcoded `empty_index` and keys solely from the entity (`lib.rs:4287-4295`); `index_validate_update_with_entity` falls back to `rec.entity_document` (`lib.rs:4371-4376`); `batch_update_preflight` does the same and carries the comment "Batch update path still keys from entity merge; empty native map until native edits land" (`lib.rs:4060-4062`). With `entity_document == None`, these produce **zero** typed keys and a unique collision passes validation. The push path is safe (`index_validate_push` reads `item.index_fields`, `lib.rs:4319-4323`) — the update path is not. The plan's risk table books unique safety under I4 ("Unique checks stay on `indexes`") and never anticipates it under I2. |
| BLOCKING | I2 / query paths | **I2 makes index-fields-only items invisible to every query and bounded-mutation path.** `entity_document` is not just echo — it is the filter substrate. `range_scan`/`claim_by_query` `consider` bails with `let Some(entity) = rec.entity_document.as_ref() else { return Ok(false) }` (`lib.rs:4612-4614`, and siblings at `4717`, `4822`, `4886`), and `plan_bounded_mutation` does `else { continue }` (`lib.rs:4954-4956`). These fail **silently** — items are skipped, not errored. I2's Out-of-scope covers "SQL projection" but says nothing about the in-memory query surface. |
| BLOCKING | I0/I2 contradiction | **The plan never decides whether `phase` is metadata or a typed index, and the two are mutually exclusive.** I0 In-scope: "≤2 typed indexes (`job_id`, `phase`)". But `index_fields` is recomputed on update *only* from `set_entity_document` (`lib.rs:2409-2416`), so maintaining a typed `phase` requires shipping a full entity document on every P2/P3 update — re-materializing precisely what I2 removes. Conversely the claim predicate the discover spec mandates is `metadata_equals`, which reads `rec.metadata`, not `index_fields` — under which the `phase` typed index is dead weight and never consulted. Two agents will build two different engines-under-test from this text. |
| BLOCKING | Gates / arithmetic | **G1 ∧ G2 do not imply G3; G3 hides two undeclared floors.** G2 at 30k ⇒ P2 = 33.3 s. P3 is the identical claim+update+release shape ⇒ ≈33 s. G1 at 50k ⇒ P4 = 20 s. Total 86.3 s, leaving **under 4 s for P1** — an implied P1 ≥ 250,000 items/s and P3 ≥ ~40,000 items/s, neither of which is a gate and neither of which appears in the Stretch table (which sets P1 ≥ 100k as *stretch*, i.e. below the level G3 silently requires). An agent that hits G1 and G2 and misses G3 has no defined action: "Stop (blocked)" fires only after I2–I5 all land. |
| BLOCKING | I4 / ADR-013 | **I4 options A and B make the projection a function of read traffic.** "Populate `claim_indexes` lazily on first `claim_by_query` for that shard" (A) and "…**and** a claim-by-query has been seen" (B) key durable index state off a non-logged event. ADR-013 requires the projection be reconstructed "replaying the log from genesis or from a snapshot at a committed `CommandPosition`" (`ADR-013:71`); the "has been seen" flag is not in the log, so post-recovery the same log yields a different projection and the first post-recovery `claim_by_query` behaves differently from the pre-crash one. Separately, the lazy build runs inside the claim path, which holds the commit section (ADR-017) — an unbounded O(N) build under the serialized lock, dismissed as "acceptable; document it" with no bound stated. |
| BLOCKING | I0 spec gap | **A cold agent cannot implement I0 without asking.** Unspecified and load-bearing: (a) **`ordering_mode` / `max_rank_error`** — not cosmetic, because `relaxed_candidates` *sorts* the selected prefix (`lib.rs:465-469, 3650-3669`), so combined with the `usize::MAX` from `select_item_claim` bounded_relaxed sorts 10⁶ keys per claim; (b) **worker/thread count** — G4's "0 duplicate leases" is vacuous at one worker, and the discover spec's "workers must not steal each other's work" presumes >1; (c) **sqlite log path / filesystem / `synchronous` setting** — the plan forbids *changing* `synchronous=FULL` but never says where the file lives; tmpfs vs NVMe is a 10× swing and the first-principles model says PLP vs consumer NVMe is 10K vs 500–2,000 commits/s; (d) **what "telemetry on" means** as a concrete flag; (e) the **10k warmup** the discover spec puts outside the clock is absent from I0; (f) `summary.json` has **no schema** — I0 says "four phases, exact counts, residual eligible 0" with no field names, units, or version, and I1 builds the ladder header from it. |
| BLOCKING | PRD conformance | **A ladder row is not a conforming evidence record.** PRD §Scale Substantiation: an evidence record must "name the deployment shape, the workload envelope, and the design/test artifact plus benchmark" and "A scale claim that cannot reference its evidence record is not publishable" (`prd.md:133-152`). The §Measurement standard schema carries `host` and `loadavg` but no storage device, filesystem, durability class, `ordering_mode`, or worker count. Plan §Goal nonetheless says "publish the run as capacity evidence." |
| WARNING | I1 | I1 permits "N=100k if 1M is not provisioned; record the N" as the baseline. Given the quadratic P2/P3 behaviour above, rates at 100k and 1M differ superlinearly; a 100k baseline cannot be compared to a 1M gate or to later 1M ladder rows. The plan gives no extrapolation rule and no prohibition on mixing Ns in one ladder. |
| WARNING | Iteration protocol | The revert line is "N=1M P4 drops more than 10% versus the previous ladder row" on a **single, unreplicated** 1M run; the risk table prescribes best-of-2 only at N=10k. On the plan's own admission ("If the host is noisier than the 13k quiet-host machine…") 10% is inside noise. There is also **no revert line for P1/P2/P3** — I2 and I3 are aimed at P1/P2 and may regress them without tripping any rule. |
| WARNING | I3 | I3's mechanism argues *against* its own prediction for G2. `ItemRecord` is `Clone` and the UpdateFields arm does a full `let mut next_rec = rec.clone()` on every update (`lib.rs:2424`). Adding a `Vec<(String, Vec<u8>)>` of framed keys to `ItemRecord` makes that clone strictly more expensive — on P2/P3, the phases G2 gates. Plan §I3 predicts "P2/P4 up". Also, "Prefer rebuild on import" is asserted without noting its constraint: `From<ProjectionImageItem> for ItemRecord` (`lib.rs:172-210`) is a free conversion with no access to `typed_index_specs`, so the import loop (`lib.rs:~1780-1824`) must be restructured, not just extended. |
| WARNING | Measurement | The ladder schema contradicts the discover spec's publication contract. `seventh-sense-phased-capacity-benchmark.md` §"What to publish" requires `mutations`, `mutations_per_s`, and `batch_p50/p95/p99_ms` **per public call** (claim / update / release) for every phase; the ladder carries only `p2_claim_p99_ms` and `p4_claim_p99_ms`. The single `batch` column also cannot represent I0's split configuration (`max_push_batch_size=1000`, `max_claim_batch_size=100`). |
| WARNING | Stop rule | **The blocked rule is unfalsifiable and does not close the loop.** "≥60% of remaining time outside `ProjectionData` apply" names no profiler, no attribution boundary, and no sampling methodology. The sqlite log append and fsync are trivially "outside apply", so once apply is optimized the condition is near-always true and the escape hatch fires immediately regardless of merit. Symmetrically, an agent landing I2–I5 with 55% inside apply has **neither** a success exit nor a blocked exit, and is told "do not invent I7." There is no attempt cap, no wall-clock budget, and no per-slice token budget. It does not prevent infinite micro-optimization; it just forbids naming the next slice. |
| WARNING | Non-goals vs model | Non-goals bans "Multi-queue horizontal scale (TP-002 E2) as a substitute for G1–G3", but `first-principles-performance-model.md` §6.3 says "Do not promise 100K completions/s on one logical stream without stating the serial-section budget." The plan sets one-queue gates and never states a serial-section budget. Given the 13k probe's own w1→w8 seals 16→5 result cited in §Diagnosis, the one-queue serial section is the thing being gated and it is unquantified. |
| NOTE | Pre-existing | `index_validate_replace` (`lib.rs:4381-4392`) passes only `replacement.entity_document` and never `replacement.index_fields` — upsert-path unique validation is already blind to index-fields-only pushes, independent of I2. Whoever lands I2 will be blamed for this; call it out in the bead so it is not conflated. |
| NOTE | I4 test | I4's proposed guard — "push N, `BatchClaim` without query, assert we did not require query-index hits" — asserts a negative with no observable surface today. It needs a counter or `#[cfg(test)]` probe, which the bead must specify or the test will be written as a tautology. |
| NOTE | I4 guard is blind | The plan cites `crates/fireweed-engine/tests/claim_cost_scale.rs` as I4's correctness guard, but that test pushes with `entity: Some(json!({"rank": rank}))` (`claim_cost_scale.rs:38-46`) — it exercises the entity path exclusively and will not catch any index-fields-only regression from I2 or I4. |

### Verdict: BLOCK

### Summary

The plan is a well-disciplined iteration protocol wrapped around a diagnosis that is measurably wrong about where the time goes. Every slice (I2–I6) targets per-item encode and `ProjectionData` apply cost, but at N=1M with a `metadata_equals` predicate the dominant cost is `select_item_claim`'s `eligible_candidates(now, usize::MAX)` — a full materialization of the eligible set on every claim, compounded by `release` returning items to the head of the priority order, which makes P2/P3 quadratic. G1 and G2 are unreachable by the entire proposed program. Independently, I0 is not implementable as written because the public `BatchUpdate` rejects leased items, so the four-phase loop the gates are priced against cannot be expressed through the API the plan restricts itself to; and I2 is scoped as a JSON micro-optimization when `entity_document` is in fact the keying substrate for update-path unique validation, `claim_by_query`, `range_scan`, and `plan_bounded_mutation` on the target cell.

Required edits before beads are filed:

1. **Add an I-slice before I2** for claim selection: either an index-backed predicate path (`claim_indexes` on `phase`) or a resume cursor so `select_item_claim` stops materializing the full eligible set. Cite `compose_impls.rs:578-607` and `lib.rs:427-437`. Until this exists, G1/G2 are not achievable and I2–I6 are unfalsifiable.
2. **Resolve the `BatchUpdate`-under-lease gap explicitly.** Either (a) state that P2/P3 use per-item `update_fields` and re-derive G2/G3 from 102 commits per 100 items, or (b) file a slice that extends `BatchUpdate` to leased items under a lease token — and reconcile it with API-003 Producer obligation 5, which currently forbids it. Delete the Non-goals sentence implying the native facade already supports lease-scoped `BatchUpdate` + `release`.
3. **Decide `phase` = metadata *or* typed index, in I0, in one sentence**, and if typed, add the missing native `index_fields` update path (`lib.rs:2409-2416`, `lib.rs:4060`) as its own slice.
4. **Rewrite I2's scope** to include: read-time echo in `fireweed-projection::to_claimed`; `index_validate_with_entity` / `index_validate_update_with_entity` keying from `index_fields`; and the `entity_document.is_none()` early-returns at `lib.rs:4612/4717/4822/4886/4954`. Add a test asserting a unique collision is still rejected on an `update_fields` of an index-fields-only item.
5. **Fix the gate set.** Either publish explicit P1 and P3 floors, or drop G3 and gate on P1–P4 individually. State what an agent does when G1+G2 hold and G3 misses.
6. **Delete I4 options A and B, or make the trigger a logged command.** As written they violate ADR-013 determinism. Add a bound on any in-claim index build (ADR-017 commit section).
7. **Complete I0's run declaration**: `ordering_mode` + `max_rank_error`, worker count, sqlite log path/filesystem/`synchronous`, telemetry flag, the 10k warmup, and a versioned `summary.json` schema. Add device, durability class, `ordering_mode`, and worker count to the ladder row so it conforms to PRD §Scale Substantiation.
8. **Make the stop rule falsifiable**: name the profiler and the attribution boundary (is the sqlite append inside or outside "apply"?), define the 50–60% outcome, and add an attempt cap so "do not invent I7" is a terminal state rather than a naming restriction.
9. **Forbid N=100k as a G1–G3 baseline** in I1, or state the extrapolation rule and mark 100k rows as non-comparable.
10. **Add P1/P2/P3 revert lines** alongside the P4 10% line, and require best-of-2 (or a stated variance) at N=1M before any revert or acceptance decision.
